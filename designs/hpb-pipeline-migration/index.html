Bamboo to GitLab CI/CD

Rebuilding delivery around environment-specific runners, reusable scripts and the checks required for an AKS deployment.

I was the main engineer for this migration at Health Promotion Board, Singapore, during my Thoughtworks engagement. This page explains the implementation behind the HPB case study ↗.

EnvironmentsSIT · UAT · PRD
Delivery platformBamboo → GitLab CI/CD
OutcomeMigration completed

01 / Environment preparation

Prepare the place where the jobs run.

The migration began with access and runner-host preparation. Each environment had one runner VM in a designated network segment, managed through VPN and a bastion host.

Host automation
I wrote Ansible scripts to manage host creation, software installation and updates. I prepared the required users and permissions, then registered the hosts as GitLab runners.
Network and identity dependencies
I prepared the NSG connectivity, registry access permissions and allowlists, and managed identity setup needed by the delivery environment.
Execution across access boundaries
I prepared and coordinated the work. The client’s support teams executed operations that were outside our team’s permitted access.

02 / Script structure

Preserve the tasks. Rework how they fit together.

I reviewed the Bamboo steps, their dependencies and their expected results. This established which tasks had to remain when the workflow moved to GitLab CI/CD.

Some inherited scripts mixed several responsibilities. I rewrote most of them, separating common functionality from task-specific work and building reusable GitLab steps around those boundaries.

a. Shared functionality

Reusable scripts and templates

Common tasks became reusable parts of the pipeline, following the client’s approach to shared functionality.

b. Specific responsibilities

Focused task scripts

Work specific to a particular task stayed separate, making the script structure clearer and easier to follow.

I also adapted the environment automation and security-scanning integration. The pipeline, its scripts and the hosts running them needed to work together in the migrated environment.

03 / SIT pipeline

From a pull request to a checked deployment.

Creating a pull request triggered the SIT pipeline automatically. The deployment counted as successful after every stage passed, including the checks after the Helm deployment.

Scanning at different points in the workflow

Fortify on Demand (FOD) provided the SAST/DAST integration. The workflow also used other scanning tools, including SonarQube. Code, dependency and image checks had separate places in the sequence; DAST followed deployment and application-status checks.

04 / Environment differences

The same release source, built in each environment.

Access between environments was strictly restricted. SIT, UAT and PRD each built and deployed from the same code for a given release version. We did not promote one immutable package or image through all three environments.

Migration order: I completed and validated the SIT/UAT migration work before progressing PRD, reusing the work already prepared. This migration sequence was separate from the release controls shown above.

05 / Validation & outcome

Complete the required checks and integration.

All stages had to pass for a SIT deployment to count as successful. The wider migration was completed after the environment, access and scanning dependencies were resolved and the required validation passed.

06 / Technical questions

Build on the implementation walkthrough.

The questions below clarify the release model and deployment checks. Further questions focus on script behaviour, repeatable builds and failure handling.

a.

Build and deployment model

Did the environments deploy the same image?

My answer

Each environment built and deployed separately from the same code for a release version. The environment model shows these separate paths and the automatic or manual release controls.

b.

Post-deployment checks

Was completing the Helm deployment enough to call the SIT deployment successful?

My answer

No. Application liveness and status checks followed Helm deployment, then DAST ran against the deployed application. Every stage in the SIT sequence had to pass.
