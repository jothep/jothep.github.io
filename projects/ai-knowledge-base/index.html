01 / Problem & contribution

Useful documentation needs
the details to survive.

Resolved software issues combine discussion, diagnostic logs, configuration and code changes. Turning that material into a knowledge article is useful operational work, but a fluent summary can still omit the fix or invent an explanation.

Build. I implemented configurable Python generation and evaluation pipelines, including a LangGraph generator–auditor loop and a local Ollama backend.

Compare. I tested simpler single-pass prompts alongside the agent workflow, using the same selected technical records within each evaluation.

Inspect. I retained outputs, scores and run records to investigate where added review helped, where it did not, and what the measurements could support.

An offline research project based on 69 purposively selected GitHub issue/PR records: 40 from Kubernetes, 20 from Ansible and 9 from VS Code. Enterprise deployment and user impact were outside the study.

03 / Decisions & trade-offs

Make complexity earn its place.

01

Keep cloud and local inference interchangeable

The model interface allowed experimentation to move from Gemini API calls to local Llama 3 through Ollama. This made local inference an option when API limits and running costs affected the experiments.

Trade-off Local hardware and smaller-model constraints become part of the operating model. Local inference does not itself establish zero cost or a compliance guarantee.
02

Give the review loop an exit

The workflow tracks the best-scored draft, stops on an auditor pass and uses a recorded fallback when it reaches the configured iteration limit. Batch outputs make these outcomes inspectable.

Trade-off A completed run may still be an auditor-rejected fallback. Completion, review acceptance and factual correctness are separate signals.
03

Keep simpler baselines in the comparison

The project began by exploring multi-agent review, then added single-pass CoT as a simpler alternative. The retained comparisons gave a reason to question the extra review stage.

Trade-off The judge is another model. Scores help compare these saved runs, while the study's evaluation design limits stronger claims about accuracy or causation.

04 / Results & interpretation

Measure the difference.
Keep the conclusion in scope.

Single-pass CoT received the highest average score in the retained three-way comparison. Adding a same-model reviewer in a separate experiment showed no statistically significant benefit.

The figures use stored capstone results, recalculated on 2 October 2026. No model generation was rerun for this portfolio review. Scores come from the configured LLM judge and do not represent an objective accuracy percentage.

Run 08: LLM-judge scores on a 0–100 scale
Workflow Mean Sample SD
Single pass 79.88 10.25
Multi-agent 76.74 14.60
Single-pass CoT 91.01 6.45

CoT scored 14.28 points above the multi-agent workflow in this run (paired t-test, p ≈ 1.65 × 10 −13 ). This is evidence about these samples and this judge configuration; it does not establish that one architecture is universally superior.

The reviewed outputs averaged 0.90 points lower (95% confidence interval for the paired difference: −4.53 to +2.73; p = 0.6232). The data did not demonstrate a benefit from this review loop. They also do not establish a reliable degradation effect or its cause.

Evaluation limits and what the review corrected
  • The sample was purposive, with uneven representation across three open-source projects. It does not establish performance across enterprise support work.
  • Candidate method names and their ordering were visible to the judge. A model judge may introduce ordering, style or self-preference biases.
  • Single-pass CoT saved the full response; the multi-agent CoT path removed reasoning text on fresh generation but retained it on cache hits. These differences limit claims about a tightly controlled comparison.
  • Cached outputs were not keyed by a complete model, prompt and input version. Archived records do not include a model digest, seed and full environment manifest.
  • Only the score-based evaluation was confirmed in the inspected code and retained results. Earlier descriptions of blind scoring and ROUGE-L are not used as verified claims here.
  • Generation also receives PR diffs. This case does not claim the generator was isolated from the reference fix, or that the reviewer experimentally proved an information-loss mechanism.
  • Recorded durations include possible retry waits and lack controlled hardware or warm-up conditions. They are not presented as a speedup benchmark.

05 / Illustrative example

From a resolved issue
to a usable knowledge note.

This small example shows the intended transformation and the details an evaluator would need to check.

Handwritten, synthetic example. Created for this case study. It is not an original ticket, model output or measured result.

Example input

A worker skips its final batch

A batch worker receives 23 records with a batch size of 10. It processes 20 records and leaves three behind without reporting an error.

The loop calculated its batch count using integer division. The fix iterates over record offsets, including the final partial batch. 

for start in range(0, len(records), batch_size):
    process(records[start:start + batch_size])

The proposed regression check uses 23 records and checks that every record is processed once.

Example knowledge note

Preserve the partial batch

Symptom
The final three records remain unprocessed when 23 records are handled in batches of 10.
Cause
Integer division counts only complete batches.
Resolution
Iterate from zero to the record count in batch-size steps. Each slice includes the available records, including a shorter final slice.
Verification
Check a non-multiple batch size and assert that all input records are processed exactly once.

A review should preserve the boundary condition and the actual fix, without inventing infrastructure failures or claiming broader validation than the input supplies.
