01 / My remit

Own the migration, work across the boundaries.

During my time at Thoughtworks, I supported a government health platform in Singapore. I was the main engineer responsible for a later phase of Azure environment migration and CI/CD rebuilding, alongside day-to-day support for the platform and its development teams.

Environment and workflow

The work covered system integration testing (SIT), user acceptance testing (UAT) and production environments, moving to isolated Azure Kubernetes Service clusters and rebuilding the inherited Bamboo delivery workflows in GitLab CI/CD.

Engineering responsibility

I did the main implementation work and guided another DevOps engineer through some repetitive scripts and steps. Restricted operations were executed by the client’s support teams through service requests.

02 / Delivery rebuild

Reconstruct the workflow around its dependencies.

I traced the inherited workflows step by step to establish how the scripts, settings and functions fitted together. That investigation guided the parts I rewrote and the configuration I re-established before testing the rebuilt setup.

a. Pipeline structure

Reusable GitLab steps

I rebuilt the Bamboo workflows as GitLab CI/CD, creating reusable pipeline steps and adapting the scripts and settings needed for the migration.

b. Environment automation

Ansible adaptation

I rewrote Ansible automation for the migrated environment. Runner setup, operating-system compatibility and package dependencies all had to fit the new execution environment.

c. Credentials and connectivity

Vault and private endpoints

I implemented Vault integration for startup credential injection and developed its backup approach. I also introduced private endpoints for internal services.

d. Shared delivery

Guidance and validation

Another engineer completed some repetitive scripts and steps under my guidance. I tested the rebuilt setup while coordinating the access and supporting changes needed from other teams.

03 / Access & dependencies

A pipeline change could depend on several teams.

In restricted environments, even queries could require a service request executed by the client’s support team. Requests often took several days. I had to work through those handoffs to obtain information, progress the migration and validate the changes.

A material migration blocker

Fortify on Demand access and setup

Static and dynamic application security testing (SAST and DAST) were mandatory for this project. The subscription and access needed for Fortify on Demand became a major migration blocker.

I repeatedly coordinated with the client, who contacted the relevant support teams and external provider. The required permissions were secured, the configuration was completed correctly and validation passed. The migration then finished successfully.

04 / Terraform knowledge sharing

Import success was only part of the check.

I wrote Terraform plan and Azure resource-import materials and used them in sessions with client staff and project teammates. The examples made the relationship between configuration, recorded state and actual cloud resources concrete.

  1. An external change and an old configuration

    The guide documented sandbox experiments around AKS upgrades performed outside Terraform. One captured plan proposed returning the cluster to the older version still declared in its configuration.

  2. Import followed by configuration review

    Other screenshots recorded updated configuration, a successful sandbox import and a final no-change plan. These were experiments that included environment rebuilds, rather than one continuous production recovery.

  3. Understand what a no-change plan covers

    Some attributes were deliberately ignored. The final plan therefore did not verify every attribute. The teaching point was to review the resulting plan and configuration, rather than treating a successful import as the end of the work.

05 / Outcome & basis

The migration was completed.

The environment and delivery rebuild progressed through the required access, configuration and validation work. I combined hands-on implementation with colleague guidance and coordination across client-controlled execution boundaries.

This case brings together the implementation work and the coordination needed to complete the migration. The successful outcome comes from my confirmed project account; the retained checklist records an earlier, intermediate stage.
