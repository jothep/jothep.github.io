01 / Role & daily work

Supporting the platform and its development teams.

As a Thoughtworks DevOps Engineer on Singapore’s Health Promotion Board (HPB) engagement, my role combined day-to-day Azure and AKS support with larger environment and delivery changes. I worked directly with development teams and was the main hands-on engineer for the environment migration and Bamboo-to-GitLab rebuild.

Day-to-day platform and delivery support

I handled routine operational work for the Azure and AKS environments, helped developers investigate environment and delivery issues, and worked through pipeline problems to get build and deployment workflows running. This included reviewing scripts and configuration and checking changes with the teams.

A major delivery within that role

The migration covered system integration testing (SIT), user acceptance testing (UAT) and production environments, moving to isolated AKS clusters and rebuilding Bamboo workflows in GitLab CI/CD. I did the main implementation work and guided another DevOps engineer through some repetitive scripts and steps.

02 / Delivery rebuild

Why did you rewrite most of the scripts?

I rewrote most of the inherited scripts, retaining very little unchanged. Some Bamboo workflows embedded their functionality in bespoke Bash scripts. The move to GitLab CI/CD changed how those functions fitted into the pipeline.

I rebuilt them as more general-purpose scripts that could be reused across pipeline steps. This matched the client’s approach of combining shared functionality with custom scripts and made the script structure clearer. I traced the original workflows, scripts and settings, then re-established the configuration and tested the rebuilt setup.

a. Pipeline structure

Reusable GitLab steps

I organised the rebuilt workflow around reusable functionality and the custom scripts needed for the migrated environment.

b. Environment automation

Ansible adaptation

I rewrote Ansible automation for the migrated environment. Runner setup, operating-system compatibility and package dependencies all had to fit the new execution environment.

c. Credentials and connectivity

Vault and private endpoints

I implemented Vault integration for startup credential injection and introduced private endpoints for internal services.

d. Shared delivery

Guidance and validation

Another engineer completed some repetitive scripts and steps under my guidance. I tested the rebuilt setup while coordinating the access and supporting changes needed from other teams.

03 / Cross-team coordination

Working across team boundaries.

The team’s CI/CD pipelines ran independently of the external service-request process. For deployments, we coordinated release timing with the Product Owner (PO).

Some migration tasks and operations or queries in restricted environments required coordination outside the team. The client’s support teams handled the relevant service requests, which often took several days. I followed up on these requests and used the returned information to progress the environment and migration work.

A migration setup blocker

Fortify on Demand access and setup

Static and dynamic application security testing (SAST and DAST) were mandatory for this project. During the migration, obtaining the subscription and access needed to set up Fortify on Demand became a major blocker.

I repeatedly coordinated with the client, who contacted the relevant support teams and external provider. The required permissions were secured, the configuration was completed correctly and validation passed. The migration then finished successfully.

04 / Delivery outcome

The migration was completed.

The environment and delivery rebuild progressed through the required access, configuration and validation work. I combined hands-on implementation with colleague guidance and coordination across client-controlled execution boundaries.

Sharing practical Terraform guidance

I also prepared Terraform plan and Azure resource-import materials and shared them with client staff and teammates. Using sandbox examples, I explained how configuration, Terraform state and actual Azure resources can differ, and why a successful import still needs careful plan review.
