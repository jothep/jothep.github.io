01 / GitOps & platform support

GitOps delivery on an AWS/EKS platform.

As a Thoughtworks Cloud Infrastructure Engineer on the SadaPay engagement, I supported AWS/EKS infrastructure, provisioned resources with Terraform and worked with Argo CD and GitHub Actions for GitOps delivery.

The GitOps setup was already established when I joined. My experience came from using it as part of the platform work, alongside infrastructure provisioning and support. This delivery model is a defining part of the engagement.

GitOps with Argo CD

In this model, Argo CD compares an application’s desired state in Git with its live Kubernetes resources. Sync status and application health are separate signals: matching the declared configuration is only one part of understanding a deployment.

The platform also used Istio and Gloo. One concrete example of my work was analysing existing gateway configuration and drawing a request-flow sketch to explain a login redirect issue to the client team’s other DevOps engineers and lead.

02 / Gloo & Istio

Understanding the platform’s service networking.

Istio was part of the platform’s service-mesh environment. The example here focuses on Gloo gateway configuration: I analysed existing routing values to understand how a request was matched, rewritten and forwarded to the application.

Match
Path, method, header and query criteria determine which route handles a request.
Transform
Rewriting changes the path presented to a downstream service.
Forward
An upstream destination and route-specific settings describe the next step.

The retained Helm values include several route groups with their own limits and timeouts. Reading these settings provides context for tracing a request beyond its public URL and examining what the downstream application receives.

03 / Investigation & communication

HTTPS at the browser. HTTP in the redirect.

I drew a request-flow sketch and used it to explain the login behaviour to the client team’s DevOps colleagues and lead. The discussion connected the browser-facing URL, the proxy path and the callback address sent to the identity provider.

The sketch followed a request through a load balancer and gateway to an administration interface. It showed HTTPS at the browser-facing entry and HTTP on the next hop, then examined the separate authorization redirect.

The comparison I explained

The callback scheme changed the visible result.

My sketch recorded an HTTP redirect_uri and a 400 response from the identity provider. Manually changing the callback address to HTTPS reached the provider’s login screen.

The drawing brought the configuration and the browser’s behaviour into one discussion. It made the distinction visible: entering the application over HTTPS did not mean the callback URL sent to the identity provider also used HTTPS. This gave me a concrete way to explain the issue across the gateway and application boundaries.
