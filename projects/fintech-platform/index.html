01 / Platform context

Working within an established cloud platform.

As a Thoughtworks consultant on the SadaPay engagement, I supported AWS/EKS infrastructure, used Terraform for resource provisioning and worked within an existing Argo CD and GitHub Actions delivery setup.

The retained materials offer a closer view of the environment: non-production gateway configuration fragments and a sketch of a Kafka UI login investigation. Together, they provide a starting point for explaining request routing and the boundary between a browser-facing URL and the application behind a proxy.

The role summary describes my confirmed responsibilities. The technical sections examine retained project material separately from that broader role.

02 / Reading the routes

A route is more than a destination.

The retained configuration contains Helm values for several Gloo gateway route groups. They describe how requests can be matched, rewritten and sent upstream, with route-specific limits and timeouts.

Match
Path, method, header and query criteria determine which route handles a request.
Transform
Rewriting changes the path presented to a downstream service.
Forward
An upstream destination and route-specific settings describe the next step.

A retained deployment helper assembles environment-specific values for a Helm release. The available fragments show how configuration was organised; without the chart templates, complete inputs or execution records, they do not establish the rendered resources or deployment result.

03 / Following the redirect

HTTPS at the browser. HTTP in the redirect.

The troubleshooting sketch records a login request passing through a load balancer and gateway before reaching an administration interface. The browser-facing connection uses HTTPS; the next hop is drawn as HTTP.

Recorded observation

The callback scheme changed the visible result.

The sketch records an HTTP redirect_uri and a 400 response from the identity provider. Manually changing that callback address to HTTPS reached the provider’s login screen.

This comparison makes the callback scheme a useful investigation lead. It does not establish the underlying cause or demonstrate a completed sign-in.

04 / What remains to verify

Keep the observation separate from the outcome.

Observed in the sketch

An HTTP callback address was associated with a rejected authorization request. An HTTPS callback reached the login screen.

Still unverified

Where the callback scheme was selected, the final configuration change, the return callback and a successfully authenticated session.

Suggested validation for a follow-up investigation

These are proposed checks, not a record of completed project work.

  1. Compare the browser-facing URL with the callback URL generated by the application and the URI registered with the identity provider.
  2. Inspect how the externally visible scheme reaches the application, including proxy forwarding metadata, trust settings and application URL configuration.
  3. After a controlled change, verify the complete sign-in journey, including the callback and authenticated session.
